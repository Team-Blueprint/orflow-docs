title: "Sandbox vs Live Mode"
description: "Understand the current state of test and live API keys in Orflow."
icon: "flask"
---

Orflow provides four API key slots that encode **visibility** (publishable vs secret) and **environment** (test vs live). However, the test/live distinction is currently structural only — there is no separate sandbox environment or isolated data store.

## Current State

| Aspect | Test Keys (`pk_test`/`sk_test`) | Live Keys (`pk_live`/`sk_live`) |
|--------|-------------------------------|-------------------------------|
| **Base URL** | Same (`{{ API_BASE_URL }}`) | Same (`{{ API_BASE_URL }}`) |
| **Data isolation** | Shared | Shared |
| **Authentication** | Works identically | Works identically |
| **Payment provider** | Same endpoint | Same endpoint |

There is currently **no enforcement** distinguishing test from live behavior. All four key types authenticate against the same backend and access the same data.

## What Is Enforced

| Scope | Allowed Keys | Endpoints |
|-------|-------------|-----------|
| **Any key** | All four slots | Read-only resource access |
| **Secret key only** | `sk_test`, `sk_live` | Reconciliation resolve, webhook endpoint management |

## Best Practices

- **Development**: Use `sk_test` during development.
- **Production**: Switch to `sk_live` when ready for production.
- **Key rotation**: Regenerate a key immediately if it's exposed.
- **Never expose secret keys** in client-side code, mobile apps, or public repositories.

<Note>
Full sandbox/live isolation (separate databases, payment provider routing, rate limits) is planned for a future release.
</Note>
